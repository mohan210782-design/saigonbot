# RAG Architecture

This document describes the Retrieval-Augmented Generation (RAG) architecture used by the **Chikku Robotics Voice AI** backend, the models it depends on, and the runtime configuration that governs each stage. It is the reference to consult when tuning retrieval quality, latency, or the LLM/embedding models.

The pipeline lives in [`src/rag.py`](../src/rag.py) (`class RAGPipeline`). The single source of truth is the streaming method `query_stream()`; the non-streaming `query()` is a thin wrapper that consumes it.

---

## 1. Models in Use

Models are configured in `.env` (see `config.env` for the annotated template). A key design rule: **embeddings always run on Ollama**, so the ChromaDB vector index stays byte-identical regardless of which generation provider is selected.

| Stage | Provider | Model | Env var(s) | Notes |
|-------|----------|-------|-----------|-------|
| **Embedding** | **Ollama** (always) | **`mxbai-embed-large`** | `EMBEDDING_MODEL` | 1024-dim, cosine-similarity model. Used for ingestion, dense retrieval, intent classification, and the FAQ cache. Never switched to OpenAI. |
| **Generation** (current) | **OpenAI** | **`gpt-4o-mini`** | `LLM_PROVIDER=openai`, `OPENAI_LLM_MODEL`, `OPENAI_API_KEY` | Fast and cheap. Used for the final answer and query normalization. |
| **Generation** (local alt.) | Ollama | `deepseek-r1:latest` (or `llama3:8b-instruct-q4_0`) | `LLM_PROVIDER=ollama`, `LLM_MODEL` | Local fallback when no OpenAI key is available. Slower but self-hosted. |
| **Query rewrite / STT correction** | **Ollama** (dedicated) | **`mistral:7b-instruct`** | `REWRITE_PROVIDER=ollama`, `REWRITE_MODEL` | Small fast LOCAL model for fixing speech-to-text errors on proper nouns ("EST robot" → "S-Robot") and resolving pronouns. Separate from the generation provider so e.g. OpenAI generation can coexist with a local rewriter. `mistral:7b` was chosen over `llama3.2:3b` (which tended to *answer* instead of rephrase) and `phi3:mini` (unstable latency). |
| **Contextual Retrieval** (ingest-time) | **OpenAI** (dedicated) | **`gpt-4o-mini`** | `CONTEXTUAL_EMBEDDINGS_ENABLED=true`, `OPENAI_CONTEXT_MODEL` | Generates a 1-2 sentence context prefix per chunk (Anthropic technique) BEFORE embedding, so each chunk is self-contained. Cached to `data/context_cache.json` so re-ingest of unchanged chunks is free. |
| **Reranking** (Layer 3) | Local (cosine) | reuses `mxbai-embed-large` | `USE_RERANKING=true`, `RERANKER_BACKEND=cosine` | Re-scores the fused shortlist by cosine similarity. Lightweight and crash-free. |
| **Reranking** (optional alt.) | FlagEmbedding | `BAAI/bge-reranker-v2-m3` | `RERANKER_BACKEND=cross_encoder` | Cross-encoder, best accuracy but loads a 2.2 GB model and can segfault on some torch/Windows combos. `auto` mode tries this and falls back to cosine on caught errors (a segfault is **not** catchable). |
| **Lexical search** (Layer 2) | `rank_bm25` | BM25Okapi (alias-aware) | `HYBRID_SEARCH_ENABLED=true`, `BM25_CANDIDATES`, `RRF_K` | Keyword matching fused with dense retrieval via Reciprocal Rank Fusion. The tokenizer normalizes entity aliases (from `data/entity_glossary.json`) BEFORE tokenizing, so STT variants ("s robot", "watch guards") map to the same canonical tokens as the stored chunks. Falls back to dense-only if `rank_bm25` is missing. |

### Active configuration snapshot (from `.env`)

```
LLM_PROVIDER=openai
OPENAI_LLM_MODEL=gpt-4o-mini
EMBEDDING_MODEL=mxbai-embed-large
USE_RERANKING=true
RERANKER_BACKEND=cosine
HYBRID_SEARCH_ENABLED=true
LLM_QUERY_REWRITE=true
REWRITE_PROVIDER=ollama
REWRITE_MODEL=mistral:7b-instruct
CONTEXTUAL_EMBEDDINGS_ENABLED=true
FAQ_CACHE_ENABLED=false       # disabled — caused false-positives on product queries
BM25_CANDIDATES=30
DENSE_CANDIDATES=30
RERANK_K=7
MAX_CONTEXT_TOKENS=1500
```

> ⚠️ The real `OPENAI_API_KEY` lives in `.env` (git-ignored). Never paste it into documentation or commit it. If it leaks, rotate it immediately in the OpenAI dashboard.

### Why embeddings are pinned to Ollama

ChromaDB stores vectors produced by a specific embedding model. If embeddings were generated by OpenAI at ingest time but queried with Ollama (or vice versa), the vector spaces would not match and retrieval would return garbage. Pinning embeddings to Ollama means you can freely switch the **generation** provider (Ollama ⇄ OpenAI) without ever re-ingesting.

## 2. High-Level Pipeline

`query_stream()` runs a **grounded-first** flow. The LLM is *never* called with empty context — that was historically the main source of fabricated facts. Every query passes through these stages in order; the first stage that produces a confident answer short-circuits the rest.

> **Note (2026-07 reform):** Layer 1 (FAQ cache) is now **DISABLED** by default — it caused false-positives where product queries like "Tell me about S robot" matched a leadership FAQ at cosine ≥ 0.75 (shared surface form "tell me about X") and never reached retrieval. All content questions now go through the hybrid retrieval layer. The code is kept intact for a possible stricter re-enablement (`FAQ_CACHE_ENABLED=true`).

```
 [1] Intent classification
        │  (embedding-based, shares the query embedding with retrieval)
        ▼
 [2] Deterministic templates  ──► CONVERSATIONAL / core-IDENTITY  →  done (<50 ms)
        │  (greetings, "who are you", "what can you do")
        ▼
 [3] Layer 1 — FAQ cache      ──► DISABLED (FAQ_CACHE_ENABLED=false) — see note above
        │  (kept for opt-in; was causing product-query false-positives)
        │  emit {type:"filler"} signal to the frontend (always, since we proceed to slow path)
        ▼
 [4] Multi-hop decomposition  ──► (optional, QUERY_DECOMPOSE_ENABLED) split
        │  compare/multi-entity questions into per-entity sub-queries
        ▼
 [5] Conditional query rewrite  (only short / pronoun / context-bearing queries)
        │  (dedicated LOCAL model — mistral:7b — for STT error correction;
        │   entity glossary injected so "es robot" → "S-Robot")
        ▼
 [6] Layer 2 — Hybrid search   (BM25 alias-aware + Dense + RRF fusion)
        ▼
 [7] Layer 3 — Rerank          (cosine or cross-encoder)
        ▼
 [8] Context construction      ──► dedup + lost-in-the-middle reorder + truncate
        │  (chunks at context start+end, mid-relevance in the middle;
        │   capped at MAX_CONTEXT_TOKENS)
        ▼
 [9] KB enrichment             (light, semantic top-3 supplement)
        ▼
[10] Context present? ──► YES → LLM generation (grounded, with citation rules) → done
                     └─► NO  → graceful "I don't have that detail" fallback
```

Each `yield` from `query_stream()` is a pipeline event that the `/chat/voice` endpoint forwards to the frontend as a Server-Sent Event. The non-streaming endpoints (`/chat/text`, `/query`) collect these and return the final response dict.

### Response `source` tags

Every final response is tagged for debugging/telemetry:

| `source` | Meaning | Typical latency |
|----------|---------|-----------------|
| `deterministic` | Handled by a template (greeting / identity) | <50 ms |
| `faq_cache` | Layer 1 FAQ hit (string + embedding cosine) | <50 ms |
| `llm` | Grounded LLM synthesis from retrieved context | 4–6 s |
| `fallback` | No grounded context found — graceful decline | <50 ms |

## 3. Stage-by-Stage Detail

### Stage 1 — Intent classification (`intent_classifier.py`)

The query is classified into an `IntentType` + `IntentCategory` using three layers, in order:

1. **Regex overrides** — deterministic rules for cases the embedding model can't be trusted with: leadership keywords (`ceo`, `founder`, `who owns`), polite declines (`no thanks`), standalone acknowledgments (`ok`, `sure`), and the critical negative rule that `what is chikku <something>` is a factual KB question, **not** identity.
2. **Embedding classifier** — cosine similarity between the query embedding and an exemplar library (4–8 example phrases per intent). Max-per-intent wins. If the best score is below `INTENT_CONFIDENCE_THRESHOLD` (default `0.65`), the query is routed to `CLARIFICATION_NEEDED` (i.e. to retrieval).
3. **Regex fallback** — used only if the embedding provider is unavailable, so the server never bricks. The query embedding computed here is **reused** by retrieval, so intent classification adds no extra embedding latency in the common case.

### Stage 2 — Deterministic templates (`response_templates.py`)

Pure-conversational queries (greetings, gratitude, farewells, small talk) and the core identity questions (`who are you`, `what do you do`, capabilities) are answered by hand-written templates. This prevents the LLM from "inventing" a ChatGPT-style identity response and keeps these turns instant.

Leadership/founder questions are deliberately **not** handled here — they are factual KB queries that must flow through retrieval so the answer is grounded.

### Stage 3 — Layer 1: FAQ cache (`rag.py::_faq_cache_lookup`) — **DISABLED**

> ⚠️ **Disabled by default** (`FAQ_CACHE_ENABLED=false`) since the 2026-07 reform. The cache caused false-positives where product queries like *"Tell me about S robot"* matched a leadership FAQ at cosine ≥ 0.75 (shared surface form "tell me about X") and never reached retrieval, returning the wrong answer. All content questions now flow through hybrid retrieval. The code is kept intact; re-enable with `FAQ_CACHE_ENABLED=true` only if you reintroduce a stricter matching gate.

When enabled, the original behavior was: two checks both gated by `FAQ_CACHE_ENABLED` — (a) string match + cosine validation, (b) strict embedding cosine ≥ `FAQ_EMBEDDING_THRESHOLD`. A hit returned in **<50 ms** and skipped the entire retrieval + LLM stack.

### Stage 3.5 — The filler signal

Because the FAQ cache is now disabled, the pipeline always proceeds to the slow hybrid-retrieval + LLM steps for content questions. If `FILLER_SIGNAL_ENABLED=true`,
`query_stream()` immediately yields `{"type": "filler"}` *before* those steps. The frontend then speaks a filler sentence (text is owned by the frontend), stops it when the real response arrives, and speaks that instead. Only the `/chat/voice` endpoint emits this event. See
[VOICE_FILLER_GUIDE.md](./VOICE_FILLER_GUIDE.md).

### Stage 4 — Multi-hop decomposition (`rag.py::_decompose_query`) — *optional*

When `QUERY_DECOMPOSE_ENABLED=true` (default off), comparison / multi-entity questions ("compare S-Robot and WatchGuard6S", "X vs Y", "difference between") are split into per-entity sub-queries by the rewrite LLM. Each sub-query is then retrieved independently and results are merged (deduped) before reranking. This ensures both entities surface their own chunks instead of one dominating the other. Off by default — opt in only if you ask many comparison questions, since it adds an LLM call.

### Stage 5 — Conditional query rewrite (`rag.py::_rewrite_query_llm`)

The query is rephrased into 2–3 variants to improve recall on paraphrases and to **correct speech-to-text errors** — critical for Voice AI where proper nouns are routinely mangled (*"EST robot"* → *"S-Robot"*, *"watch guards"* → *"WatchGuard6S"*).

**Dedicated rewrite provider** (`REWRITE_PROVIDER`, default `ollama` with `REWRITE_MODEL=mistral:7b-instruct`): a small fast LOCAL model separate from the generation provider, so e.g. OpenAI generation can coexist with a local rewriter. The entity glossary (`data/entity_glossary.json`) is injected into the rewrite prompt so the model knows the canonical vocabulary and can fix STT mangling. `mistral:7b` was chosen over `llama3.2:3b` (which tended to *answer* instead of rephrase) and `phi3:mini` (unstable latency).

Rewrite is **conditional** (`_should_rewrite`): it only runs when the query is plausibly ambiguous — short (`< REWRITE_MIN_WORDS`, default 4 words), contains a pronoun (`it`/`this`/`that`/…), or has conversation history. Clear, specific queries skip the LLM call entirely, saving latency for the majority of traffic. Results are LRU-cached and always include the original query as the first variant, so retrieval quality never drops below baseline.

### Stage 5 — Layer 2: Hybrid search (`rag.py::_hybrid_retrieve`)

For each query variant, two retrievers run and their results are fused:

- **Dense retrieval** — cosine ANN search over ChromaDB embeddings (`DENSE_CANDIDATES`, default 30). Each chunk's embedding was computed over its **contextualized** text (see Ingestion below), so dense similarity already encodes chunk provenance.
- **BM25 retrieval** — lexical keyword scoring via `rank_bm25` (`BM25_CANDIDATES`, default 30). **Alias-aware**: the tokenizer (`_bm25_tokenize_aliasaware`) normalizes entity variants from `data/entity_glossary.json` BEFORE tokenizing, so "s robot", "es robot", "watch guards" all map to the same canonical tokens as the stored chunks. This is what makes Voice AI STT-mangled queries retrieve the correct product. Disabled transparently if `rank_bm25` is not installed.

Fusion uses **Reciprocal Rank Fusion (RRF)** with constant `RRF_K` (default 60). RRF merges the two ranked lists by `Σ 1/(k + rank)`, so a document that appears high in *either* list surfaces. Results are deduplicated by document ID. A `SIMILARITY_THRESHOLD` (default 0.55 cosine distance) drops anything too dissimilar — this is the primary hallucination guard, since ChromaDB would otherwise always return `top_k` chunks regardless of relevance.

### Stage 7 — Layer 3: Rerank (`rag.py::rerank`)

The fused shortlist is re-scored and trimmed to `RERANK_K` (default 7). Backend selected by `RERANKER_BACKEND`:

- `cosine` (default) — re-embed each candidate and score by cosine to the query. Same embedding model as retrieval; cheap and crash-free.
- `cross_encoder` — `BAAI/bge-reranker-v2-m3` scores query/document pairs. Best accuracy, but loads a 2.2 GB model and can segfault on some torch/transformers/Windows builds (a segfault cannot be caught).
- `auto` — try cross-encoder, fall back to cosine on any *caught* error.

### Stage 8 — Context construction (`rag.py::_construct_context`) — *new*

Before formatting the retrieved chunks into the LLM context string, three quality improvements run:

1. **Dedup** — collapse near-duplicate chunks (same normalized text, ignoring the contextual-retrieval `<Context: ...>` prefix), keeping the highest-scored copy. Hybrid retrieval + KB enrichment often surface the same fact via multiple paths.
2. **Lost-in-the-middle reorder** — LLMs attend best to the START and END of a long context, so the most-relevant chunks (by rerank score) are placed at the extremes and the least-relevant in the middle via an interleave pattern.
3. **Truncate** — cap total context at `MAX_CONTEXT_TOKENS` (default 1500, ≈4 chars/token) by dropping the lowest-relevance chunks first; always keeps the top-1.

### Stage 9 — KB enrichment (`rag.py::_kb_enrichment`)

A light supplement: when hybrid retrieval returned a small set, related structured KB chunks (from the same detected topics) are scored by cosine to the query and the top 3 (above a 0.35 floor) are appended to the context. This is supplementary, not load-bearing — hybrid retrieval already broadens recall.

### Stage 10 — Generation & grounding (`rag.py::generate_response`)

If any grounded context exists, the LLM synthesizes the final answer from it. The system prompt (`data/system_prompt_robotics.txt`) is loaded once at init and combined with: the welcome message (first turn of a session only), the static company info section, and the retrieved context injected at the `{context}` placeholder. Conversation history is sanitized to user turns only (to avoid assistant-response contamination). The output is then passed through the response validator.

The system prompt encodes **citation & grounding rules**: answer ONLY from context; if asked about a SPECIFIC entity, focus on it (don't list all products); if context is partial, say "I don't have [detail] handy"; if empty, gracefully decline; NEVER invent. Response length is "2-5 sentences scaled to the question" (no longer the old <40-word cap, which truncated product answers).

If **no** grounded context was found, the pipeline returns a graceful *"I don't have that exact detail handy…"* response rather than calling the LLM ungrounded. (The FAQ-cache retry that used to run here is now inert since the cache is disabled.)

### Post-generation — Response validation (`response_validator.py`)

When `ENABLE_RESPONSE_VALIDATION=true`, every non-streaming response is scanned for forbidden phrases (AI disclaimers, "ChatGPT", "retrieved items", technical jargon), length, and completeness. Problematic phrases are stripped and the cleaned text is returned with a quality score. For the streaming endpoint this runs for monitoring/logging only (the stream is already sent).

## 4. Caching layers

Three independent LRU caches live on the `RAGPipeline` instance, all tuned via
`.env`:

| Cache | Key | Size env var | Default | Purpose |
|-------|-----|-------------|---------|---------|
| Retrieval cache | `(query, top_k, doc_type)` | `RAG_CACHE_MAX_SIZE` | 100 | Skip re-querying ChromaDB for repeated queries. |
| Embedding cache | normalized query text | `EMBEDDING_CACHE_MAX_SIZE` | 200 | Skip re-embedding the same string (shared by intent + retrieval + FAQ). |
| Query-rewrite cache | `(query, context_hash)` | `QUERY_REWRITE_CACHE_MAX_SIZE` | 100 | Skip the LLM rewrite for repeated queries in the same context. |

Additionally, the **FAQ question embeddings** are computed once and cached on the `KnowledgeBase` singleton (invalidated automatically if the FAQ list length changes). The **intent exemplar embeddings** are computed once on first classification and cached on the `IntentClassifier`.

## 5. Ingestion — how knowledge becomes vectors

Run `python src/ingest_robotics.py` (idempotent — existing doc IDs are upserted). It is safe to re-run whenever the JSON knowledge base changes. Re-running with unchanged chunks is FREE for the contextual step (cached).

```
data/knowledge_base/robotics/*.json   data/processed/about_robotics.txt
            │                                          │
            └──────────────┬───────────────────────────┘
                           ▼
              load_json_data()  +  load_about_chunks()
              (fine-grained chunking — see below)
                           ▼
              _inject_glossary_aliases()  ← data/entity_glossary.json
              (appends "Also known as: ..." alias line + entity_names metadata)
                           ▼
              _contextualize_chunk()  ← OpenAI gpt-4o-mini (cached)
              (prepends "<Context: ...>" provenance prefix per chunk — Anthropic technique)
                           ▼
              Ollama  mxbai-embed-large   (skips chunks that fail to embed)
                           ▼
              ChromaDB collection  chikku_robotics   (hnsw:space = cosine)
```

### Chunking strategy

Fine-grained chunks beat one giant embedding per file — short, focused texts keep each embedding signal sharp.

- **FAQ items** — one chunk per Q/A pair (`Q: …\nA: …`).
- **People / leadership** — one chunk per person (name, title, description).
- **Array items** (`products`, `technologies`, `partners`, `sensors`, …) — one
  chunk per item, prefixed with the section name for semantic context.
- **`featured_products`** — up to **four** chunks per product:
  overview, features, benefits/use-cases, and technologies/deployment.
- **Section overviews** — one summary chunk per top-level section.
- **About text** — split into paragraph-level chunks.

### Entity alias injection (`data/entity_glossary.json`)

After chunking, every chunk is scanned for canonical product names (and their STT-prone aliases) using **word-boundary** matching. When a chunk mentions an entity:

- An `Also known as: <aliases>` line is appended to the chunk text, expanding its keyword surface area so BM25 and dense retrieval both catch STT variants.
- The entity names are recorded in the chunk's `entity_names` metadata for later filtering.

The glossary is the single source of truth for canonical names + aliases (S-Robot, WatchGuard6S, Chikku Voice AI Kiosk, cobots, …). Add new products there when the knowledge base grows; both ingestion (alias injection) and the query-rewrite LLM prompt read from it.

### Contextual Retrieval (Anthropic technique)

Each chunk is prefixed with a 1-2 sentence context generated by an LLM (OpenAI `gpt-4o-mini`, dedicated via `OPENAI_CONTEXT_MODEL`) BEFORE embedding, e.g.:

```
<Context: This chunk is from the Chikku Robotics products knowledge base, describing the key features of the S-Robot solar panel cleaning robot.>
S-Robot — key features: • Replaces manual labor for cleaning dust, sand, leaves...
```

This makes each chunk self-contained so the embedding captures its provenance, not just its isolated content. Anthropic reports this cuts retrieval failures by ~49% (and ~67% when combined with reranking). Contexts are **cached** to `data/context_cache.json` keyed by `(chunk_id, text_hash)`, so re-ingestion of unchanged chunks costs nothing. Gated by `CONTEXTUAL_EMBEDDINGS_ENABLED` (default `true`); when off, chunks embed as-is.

The collection is created with `hnsw:space=cosine` because `mxbai-embed-large` is a cosine-similarity model; the ChromaDB default (L2) produces poor rankings. If an existing collection was built with the wrong metric, ingestion warns and you must delete `chroma_db/` and re-run.

## 6. Streaming protocol (`/chat/voice`)

The voice endpoint streams pipeline events as Server-Sent Events (`data: {json}\n\n`), consumed via `fetch()` + `ReadableStream` (not
`EventSource`, which is GET-only).

| `type` | When | Frontend action |
|--------|------|-----------------|
| `filler` | FAQ cache miss (slow steps ahead) | Speak a filler sentence now |
| `response` | Final answer ready | Stop filler, speak the response |
| `done` | Stream complete | Close connection, keep `conversation_id` |
| `error` | Pipeline failure | Log / surface error |

Full integration details (including sample JS) are in
[VOICE_FILLER_GUIDE.md](./VOICE_FILLER_GUIDE.md).

## 8. Tuning cheat-sheet

| Symptom | Knob |
|---------|------|
| Slow responses | Lower `TOP_K`/`RERANK_K`, set `LLM_QUERY_REWRITE=false`, disable `USE_RERANKING`, or switch to `LLM_PROVIDER=openai`. |
| Hallucinated facts on out-of-scope queries | Raise `SIMILARITY_THRESHOLD` (e.g. 0.55 → 0.5 distance is stricter; note this is a *distance*, lower = stricter). Ensure the grounding rule in the system prompt is intact. |
| FAQ question mis-routed | Raise `FAQ_EMBEDDING_THRESHOLD`. |
| Recall too low (misses relevant answers) | Raise `DENSE_CANDIDATES`/`BM25_CANDIDATES`, enable `LLM_QUERY_REWRITE`, or raise `TOP_K`. |
| Reranker crashes on startup | Set `RERANKER_BACKEND=cosine` (the cross-encoder can segfault). |
| Switching to OpenAI generation | Set `LLM_PROVIDER=openai` + `OPENAI_API_KEY` + `OPENAI_LLM_MODEL`. No re-ingestion needed. |
| Changed the knowledge base JSON | Re-run `python src/ingest_robotics.py`. |
| Changed the embedding model | Delete `chroma_db/` **then** re-run ingestion (vectors are model-specific). |
